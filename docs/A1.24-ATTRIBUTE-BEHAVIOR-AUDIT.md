# A1.24 Attribute Behavior Audit

This audit is based on the source archive stored at Source of Truth/IBSng-A1.24.tar.bz2.

## Confirmed database structures

- user_attrs(user_id, attr_name, attr_value) with primary key (user_id, attr_name)
- group_attrs(group_id, attr_name, attr_value) with primary key (group_id, attr_name) and index (attr_name, attr_value)
- ras_attrs(ras_id, attr_name, attr_value) with primary key (ras_id, attr_name) and unique index (ras_id, attr_name)

## Confirmed runtime behavior

### User

UserLoader.getUserAttrsByUserID() combines the generic user_attrs collection with normal-user, VoIP-user, persistent-LAN and caller-ID data before constructing UserAttributes.

### Group

GroupLoader loads group_attrs by group_id and converts each row into an attribute dictionary. Group actions expose change/delete operations through the Attribute Manager and database function calls.

### RAS

RasLoader loads ras_attrs by ras_id and passes the resulting attribute dictionary into the RAS implementation. ras_actions.py implements update/add/delete behavior and reloads the RAS after changes.

## Compatibility requirements

1. Preserve attribute names and string values exactly.
2. Preserve the one-value-per-(owner, attr_name) A1.24 constraint for these three tables.
3. Preserve add/update/delete semantics rather than treating attributes as an append-only bag.
4. Preserve lookup by attribute name/value because the A1.24 schema indexes it for users/groups.
5. Preserve the fact that user attributes are merged with subtype-specific and auxiliary user data during load.
6. Preserve RAS attribute reload behavior after mutation.

## ATD implementation boundary

ATD should expose one modern attribute service/repository while retaining explicit adapters for user, group and RAS ownership. The adapter must preserve A1.24 persistence constraints and behavior. Protocol consumers must use the resolved attribute state rather than bypassing the service.

Schema: source verified.

## Generic user attribute mutation — source trace, 2026-10-10

Canonical source paths reviewed:
- `core/user/user_handler.py::updateUserAttrs`: requires administrator auth, loads requested users, calls `admin_obj.canChangeUser`, then delegates to the action manager.
- `core/user/user_actions.py::updateUserAttrs` and `updateUserAttrsQuery`: builds change/delete operations through the Attribute Manager, executes the combined query, broadcasts changed user IDs, then invokes each updater's `postUpdate`.
- `core/user/attribute_manager.py::getAttrUpdaters`: only registered handlers produce updater objects; unknown names do not become generic writes.
- `core/user/attr_updater.py::useGenerateQuery`, `_changeUserAttr`, `_deleteUserAttr`: the generic updater upserts or deletes `user_attrs`; with `USER_AUDIT_LOG` enabled it records old/new values using the `_NOVALUE_` sentinel and native `insert_user_audit_log` function.
- `core/user/plugins/comment.py`: `name`, `comment`, and `phone` use this generic updater and define no additional validation or `postUpdate` side effect.
- `core/user/plugins/lock.py`: generic upsert/delete; presence of `lock` means locked.
- `core/user/plugins/multilogin.py`: converts to integer and enforces 0–255, then uses the generic updater.
- `core/user/plugins/session_timeout.py` and `idle_timeout.py`: convert to integer, then use the generic updater.
- `core/user/plugins/owner.py::OwnerNameAttrUpdater`: updates `users.owner_id` (not `user_attrs`), conditionally checks `CHANGE USERS OWNER`, and audits under attribute name `owner`.

ATD's mutation slice exposes `PUT /api/v1/users/{username}/attributes` for seven source-traced handlers: `name`, `comment`, `phone`, `lock`, `multi_login`, `session_timeout`, and `idle_timeout`. `PUT /api/v1/users/{username}/owner` separately implements `owner_name` because the A1.24 updater changes `users.owner_id` rather than `user_attrs`. It requires `CHANGE USER ATTRIBUTES` and the native `GET USER INFORMATION` dependency/owner scope, locks the target user row, preserves insert/update/delete and native user-audit semantics, and commits the ATD operational audit in the same transaction. Unsupported/specialized names are rejected rather than written directly. This is a deliberately narrow slice, not full user-attribute parity.

CI passed on code/test checkpoint `60237946c885c8f541480f9b2428f253950f7772`: 649 tests passed on both Python 3.11 and 3.12 (2 warnings each), with compile, Ruff, PHP syntax and PostgreSQL integration. Further source-vs-ATD compatibility fixtures are still required before claiming parity. Specialized attributes (credentials, caller IDs, IP allocation, charges, expiration, group reassignment, VoIP, RADIUS attributes, etc.) remain blocked until their own validation, storage, and post-update behavior are implemented.


## Additional verified slice — VoIP preferred language

Source trace: `IBSng/core/user/plugins/voip_preferred_language.py`. A1.24 registers `voip_preferred_language` with the ordinary generic attribute updater; its change and delete operations use `user_attrs`, and it does not override `checkInput`. Therefore ATD enables this one attribute through the existing generic mutation endpoint and its `CHANGE USER ATTRIBUTES` / `GET USER INFORMATION` owner-scoped authorization, rather than inventing a VoIP-specific table or permission. Native user-audit behavior is preserved. The source module describes a two-letter language code but does not enforce that constraint in its updater, so this slice intentionally does not add stricter validation absent from A1.24.


## Additional source-backed slice — save_bw_usage

`IBSng/core/user/plugins/save_bw_usage.py` defines a marker updater: changing the attribute writes `save_bw_usage` with an empty string and deleting it removes the attribute. It has no custom input or permission override, so ATD routes it through the generic user-attribute mutation boundary. ATD accepts only the empty value and preserves generic owner-scoped authorization and native user-audit logging. The bandwidth-usage consumer integration remains pending; this is mutation/storage support only.


## Additional source-backed slice — fast_dial

Source trace: `IBSng/core/user/plugins/fast_dial.py::FastDialAttrUpdater`. A change accepts a list of exactly ten entries; each entry must be empty or pass Python's digit-string check, and persistence is the comma-joined value in `user_attrs`. Delete removes the attribute. Both paths call `useGenerateQuery(..., False)`, so they explicitly suppress native user-audit logging even when `USER_AUDIT_LOG` is enabled. ATD's string API representation is ten comma-separated entries and validates count/content before writes; it preserves this audit exception for both update and delete. Full CI passed on Python 3.11 and 3.12 with 667 tests per matrix job (2 warnings each); see https://github.com/PardisMobile/ATD-Radius-Modernized-IBSng/actions/runs/38126347300. This implements mutation/storage only: fast-dial parsing, called-number redirection, VoIP plugin behavior and the native actions-manager APIs are not yet integrated.


## Consumer integration status correction — 2026-10-12

The earlier `save_bw_usage` note saying the consumer integration remains pending described the marker-only stage and is superseded by the later implementation. ATD now has an Accounting-Request consumer that writes native `internet_bw_snapshot` deltas for normal users with the effective marker. Direct A1.24 review of `core/snapshot/bw_snapshot.py`, `core/snapshot/snapshot_main.py`, `core/snapshot/onlines_loop.py`, and `core/snapshot/snapshot_searcher.py` confirms the native behavior is periodic sampling of each online instance's in/out rates, aggregation by user, and grouped reporting by `snp_date`. ATD's counter-delta model is implemented but remains partial parity; do not describe it as either unimplemented or fully equivalent.


## Source-backed runtime integration — absolute and relative expiry

Canonical source reviewed:
- `IBSng/core/user/plugins/abs_exp.py::AbsExpDate`
- `IBSng/core/user/plugins/rel_exp.py::RelExpDate`

ATD runtime now wires `abs_exp_date` and `rel_exp_date` policies into the live Access-Request pipeline. Expired users are rejected; future deadlines constrain the emitted `Session-Timeout`; overlapping absolute, relative, and configured timeouts preserve the shortest effective duration. In line with the A1.24 plugin's login hook, a user with no `first_login` receives a private candidate timestamp on the first successful login even when relative expiry is not configured; the candidate stays internal to policy evaluation and is inserted into native `user_attrs` only after the complete pipeline accepts the request. The insert uses `ON CONFLICT DO NOTHING` so concurrent first logins cannot replace an already-persisted deadline anchor. Rejected requests do not write or renew `first_login`.

Regression coverage exercises live dispatcher wiring, expired absolute/relative rejection, first-login persistence only after acceptance, absence of internal `first_login` leakage into the RADIUS response, race-safe insert method selection, and shortest-timeout composition. CI passed on Python 3.11 and 3.12 for code checkpoint `46dd1ebc17e46933d50d98a2a6146bb782808509`.

Scope remains partial: the source's continuous `canStayOnline` hooks and explicit termination of already-online instances at expiry are not yet fully reproduced. This section records source/code/test evidence; it is not an overall project-completion percentage.
