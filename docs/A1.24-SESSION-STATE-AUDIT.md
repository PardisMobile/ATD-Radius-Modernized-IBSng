# Session State Audit

Date: 2026-10-10

## IBSng A1.24

`IBSng/core/user/online.py` maintains active state in memory in `OnlineUsers.user_onlines` and `ras_onlines`. `core/user/user_pool.py` coordinates user loading and the online flag. Connection history is not the same thing as current online state.

## ATD

- `src/atd_radius/domain/radius_runtime.py::SessionRegistry` keeps live sessions in process memory and exposes `active_for_user(user_id)`.
- `src/atd_radius/domain/accounting_session.py::AccountingSessionService.apply` updates registry state and calls persistence separately.
- `src/atd_radius/application/radius_runtime.py::RadiusRuntimeHandler` routes Accounting-Request events through that service; Disconnect-Request also works with the registry.
- `src/atd_radius/infrastructure/accounting_persistence.py::NativeAccountingPersistence` writes connection history; it is not the authoritative live registry.

## Finding

ATD has an in-memory active-session registry, but it is process-local. The current API does not expose a reservation/lock coordinating Accounting Start with administrative user operations. Do not use `connection_log.logout_time IS NULL` as a substitute for the live registry.

## Required before deletion support

1. Confirm runtime process/worker topology and whether registry state is shared.
2. Define a concurrency-safe reservation coordinating Accounting Start, Stop and Disconnect with deletion.
3. Define stale-session/restart behavior.
4. Add tests for concurrent Start/Stop and multiple runtime instances.

Status: audit only; no user-deletion endpoint has been added.


## Updated concurrency boundary — 2026-10-12

The earlier finding that Accounting Start and persistence mutate state without an operation-wide lock has been partly addressed: `SessionRegistry` now exposes a re-entrant synchronization boundary and `RadiusRuntimeHandler` holds it across Accounting-Request dispatch, identity/provider resolution, session application, persistence and IP-pool Start/Stop side effects. Full CI on implementation/test HEAD `f97af48b94204ac2e7d6065d522c29d2583dc76e` passed 694 tests on Python 3.11 and 3.12 (2 warnings each).

This does not close the source-specific gap in the original finding. A1.24's `LoadedUser.online_flag` is reserved before login succeeds and remains true until the last RAS instance logs out. ATD still derives active state from RADIUS accounting and therefore cannot safely represent the Access-Accept-to-Accounting-Start interval or login-in-progress reservation; process restart/multiple workers also remain unresolved. No user-deletion or admin disconnect endpoint should be inferred safe from the lock alone.


## Authenticated RAS scope for inbound RFC 5176 control — 2026-10-20

Control requests are authenticated by the configured RAS shared secret resolved from the UDP peer IP. Session selection is now additionally constrained to that resolved native RAS ID for both Disconnect-Request and CoA-Request. This prevents a selector such as User-Name alone from mutating same-named sessions on another RAS. NAS-IP-Address and NAS-Identifier are treated as RAS-level selectors within this authenticated scope rather than requiring those attributes to be duplicated into per-session connection details. If the peer IP cannot be resolved to a native RAS, control requests fail closed with Session-Context-Not-Found (503). Regression tests cover cross-RAS isolation and unresolved-RAS behavior.


## Durable runtime session snapshots — 2026-10-20

Migration 007 adds the ATD-owned operational extension `atd_radius_live_sessions`, without replacing any native IBSng table. Active session snapshots are written in the same PostgreSQL transaction as Accounting Start/Interim/Alive/Stop. The snapshot preserves the charge/rule accumulator, octet baselines, VoIP prefix/free-second state, provider/session attributes, and termination marker. Recovery restores exact snapshots before falling back to native open `connection_log` rows; legacy rows without a snapshot are restored using the prior compatibility path and then snapshotted. This also preserves active sessions whose RAS message uses `no_connection_log`, which intentionally has no native connection-history row. A suppressed-history Stop deletes the early-opened ATD log/details instead of leaving a false open log to resurrect after restart.

Boundary: this closes loss of in-memory charging state on a single-process restart when migration 007 has been applied. It does **not** yet make concurrent multi-worker session mutation serializable; process-wide session ownership and row/advisory-lock coordination remain release blockers.


## Per-session cross-worker accounting serialization — 2026-10-20

Accounting Start/Interim/Alive/Stop now acquires a PostgreSQL transaction-scoped advisory lock derived from the complete native key `user_id:ras_id:unique_id`, reloads the durable snapshot after acquiring the lock, and replaces/removes the local registry copy before applying the event. This prevents two workers from settling or advancing the same session from independently stale in-memory counters. Stopped session snapshots are retained as bounded tombstones for seven days so duplicate Stop packets remain idempotent across workers; a new Start is still governed by the existing source-shaped session-key semantics.

This does not yet make Access-Accept login reservations or inbound Disconnect/CoA selection fully cross-worker authoritative; those paths remain separate release blockers.


## Cross-worker RFC 5176 target refresh — 2026-10-20

Before processing inbound Disconnect-Request or CoA-Request, the runtime now refreshes the authenticated RAS's session scope from durable snapshots. It locks candidate keys in deterministic order, reloads each state after the advisory lock, and removes local copies whose durable rows are gone. This lets control requests target sessions created or updated by another worker, rather than relying only on the receiving worker's stale registry.

This still does not create a durable Access-Accept/login-in-progress reservation; authorization-time MultiLogin race remains open.


## Durable login-in-progress reservations — 2026-10-20

Canonical source: `IBSng/core/user/user_pool.py::getUserByID(..., online_flag=True)`, `IBSng/core/user/loaded_user.py::setOnlineStatus/isOnline`, and `IBSng/core/user/user.py::login/logout`. A1.24 reserves the loaded user's online state while login is being attempted, before the login hooks finish. ATD now represents accepted Access-Request reservations in `atd_radius_login_reservations`. Access admission acquires a transaction-scoped per-user advisory lock, refreshes durable active sessions, includes other accepted reservations in MultiLogin policy, and excludes the exact retransmitted request from its own view. An Access-Accept records the reservation; Access-Reject does not create one. The first newly created Accounting Start/Interim session for that user/RAS consumes one reservation under the same user lock.

Reservations intentionally have no automatic short expiry: A1.24's online flag is cleared by lifecycle events rather than an arbitrary timer. If a NAS accepts authentication but never sends Accounting Start/Stop, a reservation may remain, matching the source's potential stale-online behavior; operational reconciliation remains necessary. Multi-worker authentication and Accounting Start now serialize on the same user lock. This does not yet prove complete A1.24 plugin/login-hook parity.
