# IBSng A1.24 Administrator Permission Source Audit

**Authority:** `Source of Truth/IBSng-A1.24.tar.bz2`. The archive checksum was verified by the source-audit workflow before these excerpts were printed. This document records the inspected paths; it does not replace the archive.

## Direct source findings

- `IBSng/core/admin/admin.py:92-102`: `checkPerm(name, ...)` invokes the registered permission object's `check(...)`. A missing permission or missing required argument is denied with `PermissionException`.
- `IBSng/core/admin/admin.py:105-110`: `hasPerm(name)` checks only whether the permission is present. It does **not** evaluate the permission value or contextual restrictions. It must not be used as a substitute for an authorization decision.
- `IBSng/core/admin/admin.py:112-125`: `canDo` uses `checkPerm`, except that a GOD administrator bypasses the normal permission check. `isGod()` is defined by presence of the `GOD` permission.
- `IBSng/core/admin/admin_perm.py:7-15`: multi-values are stored as comma-separated values; an empty string becomes an empty list.
- `IBSng/core/admin/admin_perm.py:41-76`: an administrator's permission value is parsed according to the registered permission's value type. `MULTIVALUE` values are split into a list; other values remain raw, including empty/None values where applicable.
- `IBSng/core/admin/perm_actions.py:35-65`: permission changes validate the permission and new value, check dependencies before adding a permission, persist the value to `admin_perms`, and reload the administrator's permission state.
- `IBSng/core/admin/perm_actions.py:92-120`: permission deletion checks dependent permissions before deleting. Dependencies are enforced by the application logic, not represented solely by the database row.
- `IBSng/core/admin/admin_loader.py:97-102,139-141`: loading an administrator loads both permission objects and administrator locks.
- `IBSng/core/admin/perms/KILL_USER.py:8-14`: `KILL USER` is a restricted single-value, user-category permission and depends on `SEE ONLINE USERS`.
- `IBSng/core/admin/perms/CHANGE_RAS.py:7-17`: `CHANGE RAS` is a no-value RAS-category permission and depends on both `LIST RAS` and `GET RAS INFORMATION`.
- `IBSng/core/admin/admin_actions.py` and native schema `migrations/001_initial.sql`: A1.24 has `admin_locks`, `admin_perms`, permission-template tables and `user_audit_log`. The latter is an attribute-change log with old/new values, not proof of a generic operational-event audit facility.

## Design consequences for ATD

1. A single shared API token is only a perimeter gate. It cannot replace the A1.24 per-administrator permission checks.
2. Keep permission presence separate from permission evaluation. A future evaluator must support no-value, single-value, multi-value and contextual/category permissions, plus explicit dependency rules and the GOD bypass only where the source permits it.
3. Before a disconnect action is exposed, resolve the actual online user/session from trusted runtime state and enforce the source-derived `KILL USER` permission and its `SEE ONLINE USERS` dependency. Do not authorize a disconnect merely because a caller knows a RAS IP or username.
4. RAS configuration mutation is a different permission (`CHANGE RAS`) and must not be conflated with disconnect authorization.
5. Do not repurpose `user_audit_log` for disconnect events without further source evidence. The operational audit storage contract remains open.
6. The web login/session bootstrap path is not yet fully traced; `IBSng/interface/IBSng/inc/admin.php` includes admin request wrappers and is not, by itself, evidence of the authentication bootstrap.

## User and group permission source findings — 2026-10-10

- `IBSng/core/admin/perms/ADD_NEW_USER.py`: `ADD NEW USER` is a no-value USER permission. `core/user/user_handler.py:addNewUsers` requires a group and owner, checks `ADD NEW USER`, and checks `CHANGE USERS OWNER` if the requested owner is not the authenticated admin. New users inherit group defaults.
- `GET USER INFORMATION` is `AllRestrictedSingleValuePermission`; the value `Restricted` permits access only when the user owner ID equals the authenticated admin ID. `All` allows all users.
- `CHANGE USER ATTRIBUTES` and `DELETE USER` are also All/Restricted permissions and both depend on `GET USER INFORMATION`. The API must check the target user's owner ID, not just permission presence.
- `IBSng/core/admin/perms/ADD_NEW_GROUP.py`: `ADD NEW GROUP` is a no-value permission used for group creation and deletion. `core/group/group_handler.py:addNewGroup` sets the owner ID to the authenticated admin ID; it does not accept arbitrary owner identity.
- `core/group/group_handler.py:listGroups` filters groups through `Admin.canUseGroup`. The source permits a group when the admin is GOD, the group owner, has `ACCESS ALL GROUPS`, or the group name is present in `GROUP ACCESS` multi-values.
- `CHANGE GROUP` is an All/Restricted permission that depends on `ADD NEW GROUP`. In the source, `All` requires access to the group; `Restricted` requires ownership. GOD bypass is applied by `canDo`, not by raw permission presence.
- `LIMIT LOGIN ADDR` is a multi-value permission whose values are comma-separated IP addresses or IP/netmask ranges. Source `canLogin` checks remote address restrictions and then native locks after password verification.

ATD's current group and user API checks implement this source-backed subset. They do not yet implement all user mutations, owner transfer, credit changes, online-user access, or the complete permission catalog. Those capabilities must not be inferred from these subset registrations.


## Independent report permissions — 2026-10-10

Direct source review found that the user-detail API must not treat `GET USER INFORMATION` as permission to read every report category:

- `IBSng/core/report/report_handler.py:63-75`: administrator connection history is gated by `canDo("SEE CONNECTION LOGS")`.
- `IBSng/core/admin/perms/SEE_CONNECTION_LOGS.py:8-16`: the permission is All/Restricted; Restricted means the admin's own users' connection history.
- `IBSng/core/report/connection.py:503-509`: Restricted connection-log queries constrain results to users owned by the authenticated admin (GOD is exempt).
- `IBSng/core/report/report_handler.py:151-165`: administrator credit-change history is separately gated by `canDo("SEE CREDIT CHANGES")`.
- `IBSng/core/admin/perms/SEE_CREDIT_CHANGES.py:8-16`: the permission is All/Restricted; Restricted limits results to the admin's own users.
- `IBSng/core/report/credit.py:161-169`: Restricted credit-change queries are scoped to users owned by the authenticated admin.
- User audit history is a third independent permission: `core/report/report_handler.py:190-203` requires `SEE USER AUDIT LOGS`.

**Parity correction applied:** `GET /api/v1/users/{username}/detail` now returns `connection_logs: null` unless `SEE CONNECTION LOGS` authorizes that user, and `credit_changes: null` unless `SEE CREDIT CHANGES` authorizes that user. Each permission's own All/Restricted scope and the source GOD bypass are evaluated independently; denied report queries are not executed. Regression tests cover missing permission, owner scope, All, and GOD.

This closes only the identified report-data exposure in the user-detail API. It does not establish complete report/RBAC parity, and `SEE USER AUDIT LOGS` is not yet exposed by this API.

## Native credit-change workflow — 2026-10-10

Source trace:
- `IBSng/core/admin/perms/CHANGE_USER_CREDIT.py`: All/Restricted, depends on `GET USER INFORMATION`.
- `IBSng/core/user/user_handler.py:150-174` and `core/user/user_actions.py:185-225`: credit changes require a valid remote address, cannot make a user's credit negative, debit administrator deposit by the per-user delta times affected user count, write `credit_change` action 2 (`CHANGE_CREDIT`), and emit the native IAS change-credit event.
- `IBSng/core/admin/admin_actions.py:132-160`: a negative resulting deposit is denied unless the administrator has `NO DEPOSIT LIMIT`; the source deposit consumption updates `admins.deposit` in the same query transaction.
- `IBSng/db/tables.sql`: native logs are `credit_change`, `credit_change_userid`, and `ias_event`; their sequences are `credit_change_id` and `ias_event_event_id`.

ATD now exposes `POST /api/v1/users/{username}/credit`. It locks the target user row and admin deposit row, enforces `CHANGE USER CREDIT` All/Restricted plus `GET USER INFORMATION`, prevents negative user credit, respects `NO DEPOSIT LIMIT`, updates user credit and admin deposit, writes both native log families and ATD's operational audit in one transaction. Request amounts are limited to the native two-decimal scale; raw credentials are never returned or audited.

Both single-user and bounded bulk credit adjustment are implemented. Bulk mode locks users in stable ID order, checks all resulting balances and owner permissions before writes, applies the delta times affected-user count to administrator deposit, and writes one native credit-change row linked to each user plus one IAS event. Credit creation parity on add-user, full deposit administration, and broader billing/quota semantics remain incomplete until separately traced and tested.



## Native admin permission mutation trace — 2026-10-10

The canonical archive checksum was rechecked before implementation. Source paths: `IBSng/core/admin/perm_handler.py`, `core/admin/perm_actions.py`, `core/admin/admin_perm.py`, and each module under `core/admin/perms/`.

- `PermHandler.changePermission`, `delPermission`, and `delPermissionValue` require an ADMIN-authenticated request and call `canDo("CHANGE ADMIN PERMISSIONS")`.
- `CHANGE ADMIN PERMISSIONS` depends on the *presence* of `SEE ADMIN INFO` and `SEE ADMIN PERMISSIONS`. `changePermission` validates the registered permission name and calls that permission's `checkNewValue`. Adding a permission checks that each declared dependency is present. Existing MultiValue permission changes append a value unless duplicated; existing NoValue permissions cannot be changed; SingleValue permissions update their value.
- Permission deletion refuses to remove a permission while any other assigned permission declares it as a dependency. MultiValue deletion verifies the type and item before removing the first matching item.
- `AllRestrictedSingleValuePermission.checkNewValue` accepts only exact `All` or `Restricted`; `GROUP ACCESS` checks the native group name; `CHARGE ACCESS` checks the native charge name; `LIMIT LOGIN ADDR` delegates to IPy address/network validation. Other source permission classes inherit the base no-op validator unless overridden.
- A1.24's `__updatePermValueQuery` for `deleteFromPermValues` filters only by `perm_name` and omits `admin_id`. ATD preserves the requested behavior but safely scopes the SQL update to both columns to prevent cross-administrator corruption.
- ATD reads the authenticated admin permissions for each request, so a separate in-memory permission-cache reload is not required. Every mutation locks the target admin row and records an ATD operational audit in the same transaction.
