## A1.24 behavior confirmed

- caller_id is a special plugin attribute; it is stored in caller_id_users(user_id, caller_id), not in user_attrs.
- caller_id maps to CallerIDUserAttrUpdater; its input is a MultiStr: comma-separated entries with numeric range expansion, default zero-padding, {n...} no-padding and {l...} explicit left-padding.
- A caller ID must not be empty. The source checks enough IDs exist for all target users, and for each target assigns one ID except the final user, who receives the remaining IDs. This is the source's multi-user allocation rule.
- Authorization is admin_obj.canChangeVoIPAttrs for every target. A1.24 maps that to CHANGE VOIP USER ATTRIBUTES, whose permission definition depends on CHANGE USER ATTRIBUTES, and uses the target user's owner scope.
- New IDs already assigned to other users are rejected. The source itself explicitly comments that this uniqueness check is not thread-safe.
- Changes replace the target user's caller_id_users rows and write native user audit under attribute name caller_id when USER_AUDIT_LOG is enabled. The native schema has a global primary key on caller_id.
- Delete removes that user's caller-ID rows and records the native user audit entry when audit logging is enabled.

## ATD implementation

- PUT /api/v1/users/{username}/caller-ids changes one user's list.
- DELETE /api/v1/users/{username}/caller-ids deletes one user's list.
- A dedicated CallerIDMutationRepository persists to the native caller_id_users table.
- Authorization is checked after locking and resolving the user, using the source-specific CHANGE VOIP USER ATTRIBUTES permission and its dependency/owner scope.
- Range expansion, global uniqueness validation, native user audit and operational audit are covered by tests.
- LOCK TABLE caller_id_users IN SHARE ROW EXCLUSIVE MODE serializes competing caller-ID changes, closing the race explicitly left unsafe in A1.24 while retaining its global uniqueness semantics.
- Both native and operational audit changes commit with the database mutation.

## Deliberate scope boundary

This increment supports one user per request. It does not implement the A1.24 bulk allocation rule where the final user receives the remaining IDs. The expression expansion has a one-million-value safety cap to prevent an authenticated API request from exhausting process memory; this is an explicit modern safety bound, not a claim that the source has the same cap.
