## Native A1.24 behavior established

1. The request requires admin authentication and `user_id`, `delete_comment`, `del_connection_logs`, and `del_audit_logs`.
2. Each target is authorized with `DELETE USER`, including the user ID and owner ID context.
3. User IDs are blacklisted in the in-memory user pool before loading/checking, and removed from the blacklist in a `finally` path.
4. Every user must be offline. Deletion rejects online users; it calculates the refund as the sum of each user's non-negative credit (`max(0, credit)`).
5. In one native query transaction, it records a `DEL_USER` credit-change entry, refunds the admin deposit by the calculated amount, writes IAS `DELETE_USER`, deletes generic attributes, normal-user credentials, plan-user rows, caller-ID rows, VoIP credentials, user/admin messages, web-analyzer rows and bandwidth snapshots, optionally deletes connection logs and user audit logs, then deletes the base `users` rows.
6. After the DB query succeeds, the in-memory admin deposit is adjusted and each user is broadcast as changed. The user-pool blacklist is always cleared in `finally`.
7. After DB commit, mailboxes are deleted for users with both `mail_quota` and `normal_username`.
8. Operationally important ordering: online check and credit refund precede deletion; database failure must not leave the deposit consumed; cache invalidation and mailbox removal happen only after successful DB work.

## ATD implementation status — 2026-10-21

The source-defined database deletion and credit-refund path is implemented in
`src/atd_radius/infrastructure/user_deletion.py` and exposed as the permission-checked
`DELETE /users` collection endpoint.

Implemented behavior:
- Stable user-ID ordering and the same `login:<user_id>` transaction advisory-lock namespace used by Access admission and Accounting reservation handoff.
- Row locking and owner-scoped `DELETE USER` permission checks before mutation.
- Fail-closed online guard covering durable live-session snapshots, Access login reservations, and legacy open successful `connection_log` rows.
- Refund of the sum of `max(0, users.credit)`, administrator deposit update, native `DEL_USER` credit-change rows (action 3), and IAS `DELETE_USER` event (type 4) when `IAS_ENABLED` is true.
- Source-defined dependent-row cleanup, optional connection-log/detail deletion and optional user-audit deletion using `is_user='t' AND object_id`, then deletion of base `users` rows.
- Transactional operational audit and rollback on repository/API failure.
- Unit coverage for refund arithmetic, online-user rejection, optional history retention, authorization and audit wiring.

Known release gaps:
- The legacy post-commit mailbox deletion hook has no configured ATD mailbox transport. The endpoint returns and audits `mailbox_cleanup_pending` usernames rather than silently claiming the external side effect succeeded.
- PostgreSQL integration coverage now verifies IAS-enabled/disabled behavior, rollback after an injected late failure, all three durable online-state guards, and that deletion waits behind the canonical per-user login advisory lock. This is a lock-coordination regression, not a complete live-Accounting race or production backup/restore exercise.
- The repository test suite does not replace a restore-and-delete exercise against a representative production A1.24 database.

This feature is implemented but is **not yet marked full A1.24 deletion parity** until those release gates are closed.

## Additional canonical online-state trace — 2026-10-10

Inspected `IBSng/core/user/online.py`, `IBSng/core/user/loaded_user.py`, and `IBSng/core/user/user_pool.py` against the checksum-verified archive:

- `OnlineUsers.user_onlines` is keyed by user ID, while `ras_onlines` tracks each live RAS instance by `(ras_id, unique_id)`. `getOnlineUsers()` returns a copy of the native online-user mapping.
- The native `internetAuthenticate`, `persistentLanAuthenticate`, and related login paths obtain a loaded user with `online_flag=True` before login processing. `UserPool.getUserByID(..., online_flag=True)` checks the deletion blacklist and sets the online flag while the user-pool loading lock is held; its source comment explicitly says this prevents releasing the user while login is in progress.
- Only after successful native login does `__authSuccessfull` add the user and RAS-instance keys to `OnlineUsers`. When an instance logs out, `__logoutRecalcEvent` removes that RAS instance and clears the loaded-user online flag only when no instances remain.

Therefore ATD's RADIUS `Accounting-Start` registry is **not yet equivalent** to A1.24 online state: it cannot represent the pre-login reservation/online flag, and a RADIUS Access-Accept is not itself proof that the RAS login has completed. The new same-process registry lock only serializes Accounting-Request processing; it does not close the Access-Accept→Accounting-Start gap. Do not use this registry alone as the final deletion guard or claim full `SEE ONLINE USERS` parity until a source-compatible login/session lifecycle boundary exists.


## PostgreSQL safety regression batch — 2026-10-23

Added isolated-schema integration coverage in `tests/integration/test_postgres_user_deletion.py` for:
- deletion/refund/credit-change and IAS behavior with IAS enabled and disabled;
- fail-closed online checks against all three durable sources: live session state, login reservations, and open successful native connection logs;
- rollback of deposit refund, credit ledger and IAS rows when a late base-user delete fails.

The tests run only when `ATD_TEST_DATABASE_URL` is configured and create/drop a uniquely named temporary schema; they do not mutate the configured database's application schema.
