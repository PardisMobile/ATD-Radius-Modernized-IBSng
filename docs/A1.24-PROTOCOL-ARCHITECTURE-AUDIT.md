# A1.24 Protocol Architecture Audit

## Purpose

This document is the source-first gate for protocol work. It records what has been verified from the IBSng A1.24 source before any new protocol extension is implemented.

## Existing protocol families found in A1.24

The source contains RAS implementations for Cisco, Cisco VPDN, MikroTik, PPPD, Persistent LAN, PortSlave, PortMaster, GnuGK, Asterisk, MVTS, Quintum Tenor, Total Control, BSAE, SER and ChilliSpot.

The RADIUS boundary handles Access-Request/Accept/Reject/Challenge, Accounting-Request/Response and Disconnect-Request/Ack/Nack families.

## Current source-level EAP finding

A source-wide inspection of the A1.24 archive found no named EAP implementation. EAP is therefore an ATD extension, not an A1.24 feature claim.

## Required analysis before EAP implementation

Before EAP is implemented, trace at least these paths in the A1.24 source:

1. RADIUS packet entry and packet decoding.
2. RADIUS dispatch and request classification.
3. Authentication flow and credential lookup.
4. User/plugin attribute loading and mutation.
5. RAS lookup, RAS attributes, ports and IPPool bindings.
6. Accept/Reject/Challenge construction.
7. Accounting request processing and connection logging.
8. Session admission, online state and disconnect behavior.
9. XML-RPC/API boundaries that can invoke authentication or session operations.
10. Database writes and stored functions involved in the above paths.

The output must identify the exact source files/classes/functions involved and the data passed between each boundary.

## EAP implementation gate

EAP may be added only after the preceding protocol audit is complete.

The implementation must:
- live at the protocol/authentication boundary;
- preserve existing IBSng user, group, RAS, attribute, accounting and session terminology;
- avoid introducing replacement database concepts for existing A1.24 tables;
- define EAP-specific state only where protocol state is genuinely required;
- include packet-level, state-transition and integration tests;
- prove that existing A1.24 authentication/accounting paths remain unchanged.

## Compatibility rule

No protocol extension is allowed to rename an existing IBSng concept. Technical class/module names may describe implementation details, but operator-facing and persisted concepts remain the A1.24 names.
