## Source paths traced

- `IBSng/core/charge/voip_charge.py`: `VoipCharge.checkLimits`, `calcInstanceCreditUsage`, `calcInstanceRuleCreditUsage`, `calcInstanceCreditUsageFromStart`.
- `IBSng/core/charge/voip_charge_rule.py`: `start`, `end`, `getPrefixObj`, `hasPrefixFor`, `anytimeAppliable`.

## Verified source behavior

- A non-empty called number makes a VoIP rule applicable only when its tariff contains a matching prefix; prefix selection uses longest-prefix match. An empty number is treated as not yet acquired by the rule applicability check.
- Effective-rule selection replaces the current candidate only when the next candidate has strictly greater priority; equal-priority rules preserve loader order.
- The first effective rule initializes the call's remaining free seconds and source-specific `min_duration`/prefix metadata. Rule transitions accrue the outgoing rule and decrement the call's remaining free seconds; free seconds are not reset for each new rule.
- Lazy settlement calculates the current rule duration after remaining free seconds. The source rounds only the final current-rule usage when the unrounded rule usage is positive; it uses `min_chargable_duration` before `round_to`.
- The non-lazy path starts from the RAS-reported call start, skips the initial free seconds, walks effective-rule intervals, sums each active prefix's CPM, and applies final-prefix rounding.
- `min_duration` is described by the source as the missed-call threshold and is also propagated into instance metadata; it is distinct from `min_chargable_duration`.
- `checkLimits` is a live scheduling path: it calculates the next rule/credit/free-seconds event and reports instances to kill when no applicable rule or credit remains. This is more than a final credit deduction.

## Increment — source-derived limit-event planner

`next_limit_event_seconds` calculates the next candidate boundary for an active VoIP call: effective rule end, a future more-applicable rule, remaining initial free seconds, or credit exhaustion. Three regression tests cover rule-end timing, free-second precedence and credit exhaustion. This is a tested scheduling primitive, **not** the complete A1.24 `checkLimits` loop: recurring recalculation, multilogin aggregation, asynchronous timers, RAS/provider kill effects and persistence across restart remain open.

## Still open — do not mark VoIP billing complete

- Source `checkLimits` scheduling and asynchronous rule/credit/free-seconds boundary events are not yet reproduced; rule changes are currently noticed on accounting events.
- The runtime does not yet propagate all source prefix metadata (including `min_duration` and prefix name) into the RAS/provider session or reproduce missed-call behavior end-to-end.
- RAS-reported call start/end times, lazy versus non-lazy calculation modes, timer-driven transitions and restart-safe session state need provider-backed parity tests.
- Credit settlement still needs end-to-end validation against A1.24's complete transaction, credit-history/IAS and call lifecycle behavior.
- No UI/installer completion is implied; both remain final-stage work.

## Timer engine foundation — 2026-10-15

Added `atd_radius.application.voip_limit_scheduler.VoipLimitScheduler`, a single-worker one-shot scheduling engine with per-key replacement/cancellation generations, bounded positive delays (1 second to 7 days), callback isolation and explicit error reporting. Tests cover callback rescheduling, cancellation, replacement while a callback is in flight, invalid delays and callback failures.

This is scheduler infrastructure only. It is **not yet wired** to production VoIP accounting, does not itself call `plan_limits`, does not issue RAS/provider disconnects, and does not persist/recover timers after process restart. Do not treat this increment as completing `VoipCharge.checkLimits` parity.


## Limit-check orchestration increment — 2026-10-15

Added `VoipLimitCheckLoop` to coordinate a scheduled per-user check, execute each returned per-session kill reason through an injected provider action, and schedule the next boundary. Transient planner failures use bounded retry backoff; failed provider actions trigger a fresh plan and retry. Regression tests cover reason propagation, repeated boundary checks, provider-action retry and invalid user IDs.

The production runtime does **not yet instantiate this loop**: a transaction-scoped production planner and concrete, source-specific RAS termination adapters must be supplied first. A1.24 provider actions are heterogeneous (for example, configured command/launcher, SNMP/RSH, H.323/Asterisk or RFC 5176 paths); a generic Disconnect request must not be substituted for them. Timer persistence/recovery after restart also remains open.


## Source-specific RAS termination adapters — 2026-10-15

Implemented tested Disconnect-Request adapters for ChilliSpot and MVTS directly from `IBSng/core/ras/rases/chilli_spot.py::killUser` and `IBSng/core/ras/rases/mvts.py::killUser`. The MVTS zero-filled response-authenticator exception is retained; ChilliSpot responses require normal RFC verification. Other provider termination paths remain unsupported and fail closed. This adapter is not yet connected to the scheduled limit loop or production runtime; VoIP parity remains incomplete.


Safety follow-up: kill decisions now carry full `SessionKey` identity (user + RAS + provider unique ID), not only the provider ID. This avoids terminating the wrong instance where two RASes reuse a session identifier. The orchestration reports unsupported providers without hot-looping. Production runtime wiring and durable restart recovery remain open.
